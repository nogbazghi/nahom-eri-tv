# Nahom Eri TV — Plan

Roadmap from current state to soft launch (M3), plus a verification pass on the M4 discovery script and a placeholder for M5. See `Nahom Eri TV — Design Document v1.md` for the full design; this file tracks execution.

This is a lightweight plan, not a `write-plan`-style TDD implementation plan — most of what's left is scripting, content, and launch logistics, not a codebase with a test suite to drive red/green against. Tickets live in `/tickets/`, one file per ticket, written to be actionable by either Nahom or a future Claude session (exact file paths and commands, not just descriptions).

## Current state

- Design doc (v1) complete, all open questions resolved (ticket 009) — including the owner decision to launch with no contact address for now (a known, tracked gap, not an oversight).
- Pilot lineup is live: 7 verified Weddings videos (ticket 002/004), pushed to GitHub (ticket 001) and served via GitHub Pages at https://nogbazghi.github.io/nahom-eri-tv/ (ticket 007).
- Page tested end-to-end locally and against live data (ticket 005) — autoplay, credit block, auto-skip, and shared-broadcast resume all confirmed working. No bugs found (ticket 006 stayed empty).
- `discover.py` (M4) verified working for real (ticket 011), but the pilot still ships on the hand-picked list — the replace-vs-wait decision is still open.
- A second design doc, `TV Guide & Multi-Channel — Design Document.md`, added a channel switcher and a second channel (Kebire). Both built, tested, and live (tickets 013–015). One follow-up remains open: Kebire's content is thinner than expected (ticket 016). Ticket 017 (stale tagline) resolved itself as a side effect of the redesign below.
- **New:** the UI was rebuilt as a Classic Guide Grid (DirecTV-style) — full-bleed player, corner badge, a toggleable EPG grid computed live from real schedule data, self-hosted fonts, mobile collapse. Prototyped first as an Artifact mockup, then ported into `docs/`. Live and verified.
- The automated curation pipeline (tickets 019–024) is designed **and built**, replacing manual script runs with a scheduled GitHub Actions job (`.github/workflows/curate.yml`, Mondays 13:00 UTC + manual `workflow_dispatch`). Key decisions: per-channel rules live in `curation/channels.yaml` (not hardcoded Python) for true generalization beyond Weddings/Kebire; a shared, pure `validate_record()` re-checks both freshly-discovered candidates AND already-stored videos every run (closing a real gap where a video could silently vanish just because a search re-ranked, not because it actually became invalid); removals apply directly to `main` (preserving the same-day-takedown commitment), while additions go through a Pull Request with a human-readable summary, so review stays lightweight without losing the safety net. See `curation/ARCHITECTURE.md` (ticket 024). It's running for real: PR #13 and the `cb8cae2` fix (off-topic content slipping into diaspora channels' search-based rules, because `type: search` channels had no topic/relevance check at all) are its first live incident and response — the missing guardrail (`text_filter`, borrowed from `type: channel`'s existing `candidate_matches()`) is now shared pipeline code, not a one-off patch.
- Cast support shipped (spec #35, tickets #38–#42, #80): the broadcast can be sent to a Chromecast or Android TV device, with the TV's own remote then driving channel switching directly. See `CHANGELOG.md` v4. Real-device verification (#91) found two bugs: the receiver auto-disconnecting after ~2 minutes (#96, fixed via `disableIdleTimeout: true`) and `#cast-button` showing (clickable, but non-functional) before a channel was picked (#73, fixed — the button now starts disabled, mirroring `#go-live`, and only enables once `app.js` reports a real channel via `neritv:channel`). One remains open: #81, remote select/Enter not reliably retuning a focused channel on at least one real device — still under active investigation; see the temporary `[DEBUG-81kd]` instrumentation in `docs/cast-receiver.html`.
- **New:** issue #82 added two more channels and a Live events mechanism for one-off occasions (weddings, festivals) a live-streaming organizer wants featured temporarily. Comedy (#84) and History (#83) both shipped as config-only `channels.yaml` additions — History as three `type: channel` sources (Association of Eritrean Studies, Mdre Bahri, and Eri-TV's own documentary catalog filtered by a title-only `text_filter: "documentary"`), all sharing `display_name: History`. Live events ship: `merge_live_events.py` merges manually-submitted events from `curation/live_events.yaml` into `videos.json` (#85), and the guide renders and tunes into their rows (#86) — a Live event row points at one real live stream rather than a computed cyclic position, and stays deliberately unwired from Cast for now. See [ADR-0015](docs/adr/0015-live-events-are-curated-manually-submitted-and-ephemeral.md) (#87) for the three Live events design decisions.
- **New:** Favorites shipped (#89): a per-row toggle (#92) and a pinned Favorites section in the guide (#93), both kept in the viewer's own browser storage only, nothing synced. See [ADR-0010](docs/adr/0010-favorites-identify-channels-by-display-name.md) for why Favorites keys off `display_name` rather than a stable channel id, and the accepted consequence (a channel rename would silently drop everyone's favorite for it).
- **New:** issue #98 proposes dedicated TV-platform apps — packaging the existing web guide/player for a smart-TV platform's own web engine (Samsung Tizen, LG webOS, Fire TV), so a viewer installs and launches it directly on the TV instead of reaching it via Cast or AirPlay from a second device. [ADR-0012](docs/adr/0012-tv-platform-support-scoped-to-tizen-webos-firetv.md), backed by `docs/research/youtube-iframe-tv-platform-support.md`, scopes this to those three only: Apple TV and Roku have no web view to host the existing codebase on, and reaching them would take a business decision (rights to self-host video) before any engineering could help. Broken into tickets #99 (Tizen), #100 (webOS), and #101 (Fire TV, blocked on device/account access — `ready-for-human`).
- **New:** Issue #105's Curation review dashboard has shipped, replacing the all-or-nothing PR review with per-candidate approve/reject (motivated directly by PR #13): reading a run's candidates (#112), approve/reject per candidate (#107), finishing a review publishes to `main` (#108), and the curation workflow waiting out an already-open review instead of overwriting it (#111). See [ADR-0013](docs/adr/0013-curation-review-dashboard-uses-client-side-pat.md) for why it authenticates with a client-side PAT rather than a backend/OAuth service — `docs/curation-review-ui.js` is the shipped dashboard, and `docs/prototype-curation-dashboard.html` is the original UI prototype it was built from. A follow-up fixed it reading `videos.json` once that file passed GitHub's 1MB Contents API limit, which silently omitted the file's content instead of erroring (#145/#146) — fixed by requesting GitHub's raw media type instead of the default JSON+base64 wrapper.
- **New:** Issue #113's first-party, anonymous per-channel viewership count has shipped, narrowing (not reversing) ADR-0008's no-client-side-observability stance: the Cloudflare Worker (#114), the app's sustained-playback beacon (#115), and the weekly git-committed snapshot (#123). See [ADR-0014](docs/adr/0014-first-party-anonymous-viewership-counting-for-curation.md). A code-review pass on the initial implementation found the Worker, the weekly export, and the client all grouped counts by `channels.yaml`'s raw key instead of Channel `display_name`, silently fragmenting any Channel fed by more than one curation source (Fenkil, Sports, Martyrs Day, Independence Day, History) across multiple KV keys/snapshot entries — fixed by `curation/pipeline.py`'s new `load_channel_display_names()` becoming the single source of truth for Channel identity everywhere a "channel" needs counting (#128; see `GLOSSARY.md`'s new **Curation source** entry for the Channel-vs-source distinction this bug turned on). The About page now discloses the anonymous counting (#125/#117). The Worker is deployed for real at `https://nahom-eri-tv-watch-counter.nogbazghi.workers.dev`, its KV namespace created, and `weekly-export.yml`'s Cloudflare secrets (`CF_ACCOUNT_ID`/`CF_KV_NAMESPACE_ID`/`CF_API_TOKEN`) set — see `worker/README.md` (#138).
- **New:** Four more Music theme channels, narrower than the existing `music`/`music_modern` rows, config-only `channels.yaml` additions each with its own tightened query list and `blocklist.yaml` entries recording noise found during live discovery: Music · Liberation Era (#47), Music · Diaspora Artists (#50), and Music · Independence Day (#51) are live; Music · Post-Independence Classics (#48) stays configured-but-dormant, deliberately left unactivated by this batch.
- **New:** A Movies channel (#134, #136, #139) — standalone, feature-length films only, explicitly excluding the serialized "Part N" dramas/sitcoms that dominate the same search space. Enforced with a `duration_min_sec` floor (~75 min) well above every other channel's spam-filter floor, rather than a label uploaders don't apply themselves. See [ADR-0016](docs/adr/0016-movies-channel-scoped-to-standalone-films.md) and `GLOSSARY.md`'s **Movie** entry.
- **New:** Vertical touch on the guide panel is fixed (#131, #133, #135) — the old swipe-paging gesture (one `.guide-row` of Focus per swipe, inherited from ADR-0001's "tablet is just another directional-input track" premise) made the guide's full channel list nearly unreachable once `channels.yaml` grew to ~25 entries. Touch is now excluded from `guideNav` entirely: vertical touch drives the browser's native scroll, and each row's own tap/click handler still selects it directly. See [ADR-0017](docs/adr/0017-touch-scrolls-and-taps-the-guide-directly.md) and `GLOSSARY.md`'s **Focus** entry.
- **New:** Ticket #69/#130 added `curation/preflight.py`: one cheap, classified API call before `jobs.yaml`'s real jobs run, so an invalid or quota-exhausted `YOUTUBE_API_KEY` fails the scheduled run fast with a specific message instead of burning part of a run's quota on jobs that were always going to fail partway through. Issue #70/#142 then added standing-issue health reporting on top: every run (success or failure) comments its outcome and estimated API-unit cost onto a single, never-closed "Curation pipeline health" GitHub issue, via `curation/health_issue.py`. See `curation/ARCHITECTURE.md`'s data-flow diagram.
- **New:** Issue #140 fixed `curate.yml`/`weekly-export.yml`'s direct-to-`main` pushes, which had been silently failing: the default `GITHUB_TOKEN` can't satisfy main's required status checks on a direct push, and `enforce_admins: false` only bypasses that for an actual human admin account, never a bot token. Both workflows now checkout with `ADMIN_PUSH_TOKEN` (a new repo secret, an admin PAT) so their pushes authenticate as that admin — restoring [ADR-0009](docs/adr/0009-ci-required-check-gates-prs-not-direct-pushes.md)'s intended behavior. Masked until now because recent `curate.yml` runs happened to have zero removals, and `weekly-export.yml` had never run for real before.
- **New:** Issue #71/#149 extended #70's health-reporting pattern to `test.yml`'s own CI: a `report-main-health` job, scoped to `push`-to-`main` events only (never `pull_request`, since branch protection already catches those), posts "CI health on main" updates to its own standing issue whenever a direct push lands a failure required checks couldn't block — the exact gap #140 exists to close in the first place.
- **New:** Issue #144/#147 shipped [ADR-0018](docs/adr/0018-silent-universal-gesture-unlock-for-safari-autoplay.md)'s Safari/iOS autoplay gesture-unlock for real: a document-level click/touchstart/keydown listener calls `player.playVideo()` once the player exists and isn't already `PLAYING`, armed across multiple gestures rather than just the first (a "remember-and-nudge-later" design was tried and confirmed by test *not* to work — WebKit only honors the unlock inside a real gesture's own synchronous handler). A no-op on Chrome/Firefox, where the player is already playing by the first gesture. Covered by a new Playwright test against a mocked `YT.Player`, plus manual end-to-end validation against real WebKit.
- **Note:** [ADR-0019](docs/adr/0019-duplicate-review-disposition-skips-the-blocklist.md) (issue #150) decides a third Review decision, Duplicate — drops a redundant Curation candidate (the same video independently discovered by two rules sharing a display channel) from the run without requiring a reason or touching `blocklist.yaml`, unlike Reject. Motivated by a real data-loss bug confirmed live on PR #143: rejecting a same-id duplicate was silently deleting the other, already-approved copy on the next scheduled run. Design only so far — the implementation ticket is still open.
- Soft launch (ticket 010) has not happened yet — tabled by the owner to do UI and curation-pipeline work first.
