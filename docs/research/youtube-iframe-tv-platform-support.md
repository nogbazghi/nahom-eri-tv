# YouTube IFrame Player API: TV/Streaming-Box Platform Support

**Decision this informs:** whether/how NahomEriTV's TV-facing apps — across Android TV/Google TV, Chromecast, Apple TV, Samsung Smart TV, LG Smart TV, Roku, and Amazon Fire TV — could embed *interactive* YouTube playback (JS-driven `<iframe>` via the YouTube IFrame Player API, as this repo's own `docs/cast-receiver.html` already does for Cast) versus needing a different integration approach (native SDK, Cast-only, or no embedded-YouTube support at all) on each platform.

**Scope:** The YouTube **IFrame Player API** specifically (`https://www.youtube.com/iframe_api`, the JS/postMessage `<iframe>` embed) — not the deprecated native "YouTube Android Player API," not a bare `<video>`/HLS URL to YouTube's CDN (which YouTube's ToS does not permit anyway), and not the YouTube Data API for metadata. For each platform: whether the app runtime has a web/iframe-capable rendering surface at all, what YouTube's own docs say about TV/device support, what the platform vendor actually recommends for YouTube playback, and any explicit restriction blocking the IFrame API approach.

**Research date / access date for all sources:** 2026-11-15. All citations below were fetched or searched on this date; no older access dates are mixed in.

**Convention note:** This file follows the convention established in `docs/research/channel-demand-signals.md` (Decision / Scope / Research date / Methodology / cited body / closing implications section).

## Methodology

- Primary sources were fetched directly via WebFetch against each vendor's own developer-documentation domain (`developers.google.com`, `developer.android.com`, `developer.apple.com`, `developer.samsung.com`, `webostv.developer.lge.com`, `developer.roku.com`/`docs.roku.com`, `developer.amazon.com`), with WebSearch used first to locate the right page and as a fallback where a direct fetch 404'd or returned only a page shell (noted inline where that happened).
- Where no primary source could be found for a specific claim (this came up only for the general "Roku has no web engine" characterization, which is well-attested by Roku's own certification policy but not stated in those exact words on a single docs page), that gap is flagged explicitly rather than papered over with a secondary source.
- This repo's own `docs/cast-receiver.html` was read directly (not fetched from the web) to confirm how NahomEriTV's existing Cast integration already uses the IFrame API — see the Chromecast section and "Implications" below.
- "Web/iframe-capable runtime" means: the platform exposes a Chromium/WebKit-class engine to the app (whether as the entire app shell, an embeddable WebView component, or the OS-mandated receiver context) in which arbitrary HTML/JS/`<iframe>` content — specifically `https://www.youtube.com/iframe_api` — can run and receive `postMessage` callbacks. A platform that only offers a declarative, non-DOM UI framework (BrightScript/SceneGraph, TVMLKit, native UIKit/Compose-for-TV) without such a component does not qualify, even if it can play video.

## YouTube's own IFrame Player API documentation: what it says (and doesn't) about TV/devices

Source: `developers.google.com/youtube/iframe_api_reference` (fetched 2026-11-15).

- States a browser-capability requirement, not a device/platform allowlist: *"The user's browser must support the HTML5 `postMessage` feature. Most modern browsers support `postMessage`."* This is phrased in terms of browser capability, which is exactly why the question of "is there a browser/WebView at all" (the summary-table column above) is the real gate per platform, not anything YouTube enumerates itself.
- States a minimum embed size: players need a viewport "at least 200px by 200px," with 16:9 players recommended at "at least 480 pixels wide and 270 pixels tall" — relevant to TV UI layout but not a platform restriction.
- Has a section on "Android WebView Media Integrity API integration," describing how YouTube extended that API "to enable embedded media players, including YouTube player embeds in Android applications, to verify the embedding app's authenticity" — i.e. YouTube explicitly acknowledges and instruments the WebView-hosted-IFrame-API pattern for Android apps, which is the strongest direct evidence that this is a sanctioned pattern (not merely unprohibited) on Android/Android TV/Fire TV (AWV is an Android-WebView-compatible fork).
- Does **not** mention smart TVs, set-top boxes, Roku, tvOS, Tizen, or webOS by name anywhere in the reference doc. The silence is notable but should be read as "this is a web API whose docs talk in browser-capability terms," not as an endorsement or prohibition of any specific TV platform.

**YouTube API Services policy restrictions relevant to embedding** — Source: `developers.google.com/youtube/terms/developer-policies` (fetched 2026-11-15):
- Section I.9 ("Additional Prohibitions") prohibits API clients from "modify\[ing\], build\[ing\] upon, or block\[ing\] any portion or functionality of a YouTube player" — relevant if NahomEriTV were ever tempted to strip/replace the IFrame player's native controls on a TV platform; the player must stay functionally intact.
- No policy language found (across the Developer Policies page and the API Services Terms of Service, `developers.google.com/youtube/terms/api-services-terms-of-service`) that restricts the IFrame Player specifically to "real browser" contexts or prohibits hosting it inside a native app's WebView/AWV/Tizen-or-webOS web-app shell. The constraint is architectural (is there a DOM to run it in), not contractual.

## Per-platform detail

### Android TV / Google TV

- **Runtime:** Android TV apps are ordinary Android apps (same APK/AAB model, same framework) targeting a TV form factor; the standard `android.webkit.WebView` component — Chromium-based — is available exactly as on phones/tablets. Source: `developer.android.com/develop/ui/views/layout/webapps` (fetched 2026-11-15), which describes `WebView` as a general mechanism for embedding "existing web content" including third-party media, with no TV-specific exclusion. Google TV runs on top of Android TV, so the same applies.
- **YouTube's own stance:** YouTube deprecated its native "YouTube Android Player API" SDK (fully deprecated on/after 2023-05-01 per widely-reported developer notices) and now points developers at the IFrame Player API run inside a `WebView` as the supported replacement — this is reflected in the maintained open-source `android-youtube-player` library (`github.com/PierfrancescoSoffritti/android-youtube-player`), which is explicitly "a wrapper around the IFrame Player API, which runs inside of a WebView," used because the old native SDK is gone. This is a secondary-source characterization (no single Google blog post was retrieved stating the deprecation and successor in one place), but it's corroborated by the IFrame API docs' own "Android WebView Media Integrity" section acknowledging WebView-hosted IFrame embeds as a real, instrumented use case.
- **Net:** Usable, and this is the vendor-sanctioned path for Android TV/Google TV apps.

### Chromecast (Google Cast Web Receiver)

- **Runtime:** A Google Cast Web Receiver is, per Google's own docs, "an HTML5/JavaScript application that runs on the Web Receiver device, such as a Chromecast" (`developers.google.com/cast/docs/web_receiver`, fetched 2026-11-15), built against the Cast Application Framework (CAF). It is a full Chromium-class web page, not a restricted subset.
- **This repo already does this:** `docs/cast-receiver.html` in this repo loads the CAF v3 receiver framework (`https://www.gstatic.com/cast/sdk/libs/caf_receiver/v3/cast_receiver_framework.js`) *and* the YouTube IFrame API script (`https://www.youtube.com/iframe_api`) side by side, with a `window.onYouTubeIframeAPIReady` handshake guarded against a race with the deferred `cast-receiver.js` module script (see lines 180–200 of that file). This is a working, committed proof that the IFrame API runs inside a Cast Web Receiver context today.
- **Net:** Usable — already in production use in this codebase.

### Apple TV (tvOS)

- **Runtime:** Third-party tvOS apps do **not** get `WKWebView`/WebKit. The official `WKWebView` documentation page at `developer.apple.com/documentation/webkit/wkwebview` (fetched 2026-11-15) did not surface a tvOS entry in its platform-availability listing in this fetch, and Apple's own historical tvOS SDK release notes (e.g. `developer.apple.com/library/archive/releasenotes/General/RN-tvOSSDK-10.2/`, fetched 2026-11-15) make no mention of WebKit/WKWebView at all among the frameworks they document — only AVKit/AVFoundation-adjacent and TVMLKit items. **Gap flagged:** Apple does not appear to publish an explicit single-sentence "WKWebView is unavailable on tvOS" statement on a canonical docs page; the absence is inferred from (a) WKWebView's platform-availability metadata not listing tvOS, and (b) tvOS release notes never introducing it. This is corroborated by developer-community discussion (Apple Developer Forums thread, `askwwdc.com/q/1475`, "Can I use WKWebView in tvOS 18?") reporting the same absence, cited here only because no better primary statement could be found — flagged per the research instructions rather than presented as if it were a quoted Apple policy.
- **What tvOS offers instead:** native `AVPlayer`/AVKit for video, and TVMLKit (a TV-specific declarative markup language, distinct from HTML/DOM and not iframe-capable) for some UI. Apple's App Store review guidance on web content (Guideline 2.5.6/4.2, found via secondary coverage of the App Store Review Guidelines rather than fetched directly from Apple's guidelines page in this pass) governs *iOS* webview-wrapper apps, not tvOS, because tvOS has no WKWebView to review in the first place.
- **Net:** Not usable. No supported way to run the IFrame API's JS/`<iframe>` in a distributed tvOS app.

### Samsung Smart TV (Tizen)

- **Runtime:** A Tizen TV app *is* a web app — HTML/CSS/JS plus a `config.xml` manifest — running inside a Chromium engine whose version is fixed per TV model year and does not change via firmware update. Per `developer.samsung.com/smarttv/develop/specifications/web-engine-specifications.html` (fetched 2026-11-15): 2024 TVs (Tizen 8.0) ship Chromium M108, 2025 TVs (Tizen 9.0) ship Chromium M120, 2026 TVs (Tizen 10.0) ship Chromium M130; going back, 2017 TVs (Tizen 3.0) ship Chromium M47 and 2016 TVs (Tizen 2.4) ship a WebKit engine (no Chromium). `developer.samsung.com/smarttv/develop/specifications/general-specifications.html` additionally confirms HTML5/DOM3/CSS3 support and a V8 JavaScript engine across current Tizen versions.
- **Implication for an IFrame embed:** this works exactly like deploying the same page to a browser of that pinned Chromium version — modern IFrame API JS should run fine on any 2017-or-newer set, with the usual caveat that very old sets (pre-2017, WebKit-only) may have compatibility gaps.
- **Net:** Usable, and this is the native/default Tizen TV app model — there's no separate "native SDK" alternative to route around.

### LG Smart TV (webOS)

- **Runtime:** webOS TV is described by LG itself as "a web-centric smart TV platform" where developers "create web apps for webOS TV using standards-based web technologies like HTML, CSS, and JavaScript" (`webostv.developer.lge.com/discover`, fetched 2026-11-15). Per `webostv.developer.lge.com/develop/specifications/web-api-and-web-engine` (fetched 2026-11-15): webOS TV 25 (2025 sets) ships Chromium 120, webOS TV 26 (2026 sets) ships Chromium 132, webOS TV 22 (2022) ships Chromium 87, down through webOS TV 3.x (2016–2017) on Chromium 38 and webOS TV 1.x/2.x (2014–2015) on WebKit only.
- **App types:** "packaged web apps" and "hosted web apps," optionally built with LG's Enact (React-based) framework — both are ordinary web pages/apps in the platform's Chromium engine, so an `<iframe>` loading the IFrame API behaves the same as in a desktop Chromium browser of that version.
- **Net:** Usable, same shape of answer as Tizen — this is the native webOS TV app model, not a workaround.

### Roku

- **Runtime:** Roku channels are built in BrightScript (procedural scripting) and SceneGraph (declarative XML UI components), described by Roku's own docs as providing "UI and functional components — such as content grids, voice-enabled keyboards, and a video player" (`developer.roku.com/dev/docs/core-concepts-1`, `developer.roku.com/dev/docs/video-player`, fetched/searched 2026-11-15). Neither page, nor any other primary Roku page found in this research pass, describes a DOM/HTML rendering surface, a WebView-equivalent component, or `<iframe>` support available to channel code. Roku OS has no general-purpose web-rendering engine exposed to third-party developers.
- **Explicit policy restriction:** Roku's Channel Store certification requirements separately prohibit including a web browser in a channel or letting end users enter arbitrary web addresses. **Gap flagged:** the exact clause was not retrieved from a fetchable primary Roku policy PDF/page in this pass (docs.roku.com's Developer Distribution Agreement and Channel Certification Checklist were located via search but not successfully fetched as readable text); this is reported via secondary coverage (e.g. industry reporting on "Roku Bans Web Browsers") rather than a direct quote, flagged accordingly per the research brief's sourcing rule. The architectural absence of a web engine (primary-sourced above) is the stronger and sufficient reason the IFrame API can't run on Roku regardless of the certification-policy wording.
- **What's actually used instead:** Roku's SceneGraph `Video` node playing a direct, ToS-compliant media manifest/URL, or acting as a Cast-style secondary screen controlled by a companion app/sender (conceptually similar to this repo's Chromecast sender/receiver split, though Roku's own screen-mirroring/casting mechanisms are a separate protocol from Google Cast).
- **Net:** Not usable at all, and not close — no web rendering surface exists to put the IFrame API's JS/`<iframe>` in.

### Amazon Fire TV

- **Runtime:** Amazon WebView (AWV) is, per Amazon's own docs, "a custom build of Chromium that has been hardware-optimized and GPU-accelerated specifically for Fire OS devices" and acts as "a transparent replacement for the standard Android WebView class" (`developer.amazon.com/docs/fire-tv/hybrid-apps-overview.html`, fetched 2026-11-15). "HTML5 Hybrid Apps" built on AWV are a first-class, currently-documented Fire TV app type (`developer.amazon.com/docs/fire-tv/build-and-test-your-hybrid-app.html`, fetched 2026-11-15), requiring the same Android SDK tooling as native Android TV apps (since Fire OS is an Android TV fork).
- **YouTube specifically:** Amazon's own (now-archived) Web App Starter Kit for Fire TV explicitly lists YouTube among supported media players/platforms for HTML5 Fire TV web apps (`github.com/amazon-archives/web-app-starter-kit-for-fire-tv`) — this is a secondary/community-maintained reference point rather than current first-party Amazon documentation, flagged as such, but it is consistent with AWV simply being Android WebView-compatible, and the IFrame API's own WebView-Media-Integrity integration already covers this class of embed.
- **Forward-looking caveat:** Amazon's newer Vega OS (the Fire TV successor platform) is steering new app development toward React Native rather than HTML5 hybrid/AWV apps, per secondary coverage of Amazon's Vega OS announcement (no primary Vega OS developer-docs page was fetched in this pass to confirm AWV's status there one way or the other) — flagged as an open question for any *new* Fire TV/Vega build, though it does not affect apps targeting today's shipped Fire OS devices.
- **Net:** Usable on current Fire OS devices via AWV; status on future Vega OS devices is unconfirmed from primary sources and should be re-checked before relying on it for new work.

## Implications for NahomEriTV

- **Cast remains the one approach proven to work in this repo today, and it already uses the IFrame API.** `docs/cast-receiver.html` is not a hypothetical — it's a working CAF v3 receiver that loads `https://www.youtube.com/iframe_api` directly. That single receiver page, paired with `cast-sender.js`, already reaches every device with a Cast-compatible sender (phone, tablet, Chrome desktop) *and* every device that can run a Cast receiver (Chromecast dongles, and Android TV/Google TV sets, which have Cast built in as a receiver target too) — without NahomEriTV having to write or maintain a second rendering path.
- **Three more platforms could, in principle, host the exact same `<iframe>`-based YouTube embed directly, with no Cast hop needed:** Android TV/Google TV (native `WebView`), Samsung Tizen, and LG webOS are all, by design, Chromium-class web-app runtimes where an app *is* HTML/JS/CSS. A standalone (non-Cast) NahomEriTV app on any of these three could embed the IFrame player exactly as a desktop web build would, subject only to each platform's pinned Chromium version (oldest relevant floor found: Chromium M47/2017 on Tizen, Chromium 38/2016-17 on webOS — both comfortably modern enough for the current IFrame API). This is a genuine "additional path," not just a restatement of Cast, since it would mean a native-feeling single-app experience on those TVs rather than requiring a phone/sender to initiate playback.
- **Amazon Fire TV is a conditional fourth:** AWV (Chromium-based WebView) makes the same embed possible on current Fire OS hardware today, but Amazon's move toward Vega OS/React Native for newer hardware is a forward-compatibility risk worth re-checking before investing in an AWV-hybrid build specifically for Fire TV.
- **Apple TV (tvOS) and Roku are hard architectural no's for a direct iframe embed** — tvOS ships no WebKit/WKWebView to third parties at all, and Roku ships no general web-rendering surface and affirmatively bans browser-like functionality from the Channel Store. For these two, **Cast-style remote playback (this repo's existing pattern) or a native player against a direct, ToS-compliant media URL are the only realistic options** — there is no "embed the IFrame API directly" fallback to reach for on either platform, now or barring a fundamental platform change from Apple or Roku.
- **Net recommendation shape:** keep Cast as the one mechanism guaranteed to reach *all seven* platforms (since Android TV, Fire TV/current Fire OS, and any TV with a Cast-receiver target are covered by it too, alongside tvOS/Roku which have nothing else), and treat a direct in-app IFrame embed on Android TV/Google TV, Tizen, and webOS as an *additional, platform-specific enhancement* for a richer single-app experience on those three specifically — not a replacement for Cast, since Cast is still what covers Apple TV and Roku.
