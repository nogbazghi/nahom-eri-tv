# Live events curate, not broadcast; are manually submitted, not pipeline-automated; and render as a new ephemeral row, not a Channel row

A Live event (spec #82) features an existing wedding's or festival's own live YouTube stream in the guide for the window around its scheduled start. Three decisions shaped that design, each diverging from an existing, more obvious precedent elsewhere in this codebase — recorded together here since they're one coherent design, not three unrelated choices. This ADR assumes the **Live event**, **Live event row**, and amended **Go to Live** vocabulary that the Live-events work (tickets #85/#86) adds to `GLOSSARY.md`.

## Curate an existing stream, don't broadcast one ourselves

A **Live event** (`GLOSSARY.md`) only ever embeds a stream an organizer is already running on their own YouTube channel — the same embed-only, never-rehosted posture every other channel already has (ADR-0003). Nahom Eri TV never produces, hosts, or ingests the stream itself; curating it costs nothing beyond what the embed-only model already costs for any other video, and the uploader already carries whatever rights exposure comes with running their own public stream — nothing about ADR-0003's embed-only reasoning turns on whether the embedded video happens to be live or pre-recorded, since in both cases it's already public and embeddable on YouTube before this app ever points at it. The alternative, Nahom Eri TV hosting or re-streaming the occasion itself, was rejected because it would require ingest/transcoding/CDN infrastructure that doesn't exist anywhere else in this app, built for what's structurally a one-off occasion, and it would shift rights and liability from "the uploader already carries it" onto Nahom Eri TV becoming the broadcaster of someone else's event.

## Manual PR-reviewed submission, not the automated search/validate pipeline

A Live event is submitted by hand-editing a new curation config file and merging it via a normal pull request — never discovered or validated by the automated curation pipeline (`channels.yaml`'s search/channel rules, `discover.py`, the shared validate/merge pass described in `curation/ARCHITECTURE.md`). That pipeline's two pillars both assume an already-published, already-measurable video: search finds new candidates via YouTube queries, and validation checks thresholds like `view_count_min`/`duration_min_sec` against metadata a video already has. A live event scheduled for the future has neither — it may carry no view count and no fixed duration before it airs — so there's nothing for either pillar to act on pre-air. PR review is the one check that does make sense before a stream exists, and it's also the same gate the pipeline's own *additions* (as opposed to removals) already go through, for the same reason: an untested addition gets a human glance before it's live. Restricting submission to admin/maintainer PRs (rather than a public request flow) is deliberately deferred scope, not a limitation of this mechanism. The alternative, extending the automated pipeline's search/validate rules to also cover Live events, was rejected because validation would have nothing to validate against before the stream exists, and because a scheduled occasion isn't something a search query discovers the way a published video's title or description is — its existence is only knowable from whoever is organizing it, which manual submission already captures directly.

## A new ephemeral "Live event row" mechanism, not an extension of Channel row

A Live event renders through a new, separate code path — a pure visibility-window function sitting alongside (not inside) the cyclic-lineup schedule module, and its own tune/render handling in the guide — rather than being folded into the existing Channel/schedule machinery. A Channel row's entire premise is a cyclic lineup with a computed live broadcast position (`GLOSSARY.md`); a Live event has none of that, just one video, one scheduled start, and a visibility window (default 2h lead-time / 24h expiry, both overridable) computed straight from wall-clock time. Reusing the Channel row path would mean teaching the cyclic-lineup module a degenerate single-video, non-repeating case it was never designed for, or special-casing its position math around an assumption (a channel always has a lineup to compute a position within) that the rest of the codebase relies on holding. A **Live event row** (`GLOSSARY.md`) also behaves differently once empty: a Channel row with nothing scheduled renders disabled, but a Live event row simply disappears from the guide the moment it's no longer visible, rather than rendering disabled — there's no "channel" left to show once the occasion has expired. This is the same boundary `GLOSSARY.md`'s "Live event" entry draws under _Avoid_ ("a Live event has no `channels.yaml` entry and no cyclic lineup — it's a different mechanism from a Channel row, not a special case of one"): this decision is what makes that true in code, not just in naming. "Go to Live" stays a single user-facing control and label across both cases (per the amended `GLOSSARY.md` entry), but its mechanism now branches on what's tuned: recompute the lineup position for a Channel, or jump to the real stream's live edge for a Live event. The alternative, modeling a Live event as a one-video Channel (a schedule entry with a single-video, non-cyclic lineup), was rejected because it would special-case the cyclic-lineup module for a case it isn't built for, and because a Channel row's disabled-when-empty semantics don't fit something that should vanish entirely once its occasion has passed.
